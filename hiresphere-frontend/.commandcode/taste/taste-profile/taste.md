# Taste Profile
- When requesting UI work, prefers UI-only implementations with no business logic or data fetching wired in (static mockups / visual design only), but still expects UI-level interactivity such as modal open/close state to work (e.g., via controlled overlay state). Confidence: 0.8
- Prefers building UI with HeroUI v3 (`@heroui/react`) components and Gravity icons (`@gravity-ui/icons`). In HeroUI v3, `Input`'s `onChange` expects a native event: use `onChange={(e) => setValue(e.target.value)}` — NOT `onChange={(value) => setValue(value)` which causes type errors. Also: `isInvalid`, `isReadOnly`, and `isDisabled` props are NOT supported by HeroUI Input and will leak to the DOM element (React console error: "React does not recognize the `isDisabled` prop on a DOM element"); instead, handle invalid/error state via conditional `<p>` tags rendered below the input with appropriate Tailwind classes (e.g., `text-danger` for errors). For readonly fields use the native `readOnly` HTML attribute; for truly disabled fields use the plain `disabled` prop alone. Also, a controlled input with `value` requires either `onChange` or `readOnly`/`disabled` — otherwise React warns "You provided a `value` prop to a form field without an `onChange` handler" and the field renders read-only. Always defensively wrap string-typed state values with `String(value)` before calling `.trim()`, `.toLowerCase()`, etc. to avoid `X is not a function` errors when values start as undefined/null. Confidence: 0.9
- Expects navigation/sidebar links to be fully functional even in UI work: real route paths, working navigation via framework router (e.g., Next.js `Link`), active-state highlighting based on the current path, and missing routes resolved (e.g., by creating placeholder pages) so every link works. Confidence: 0.8
- Likes to attach a reference image/screenshot of the desired design and asks the assistant to recreate it pixel-for-pixel. Confidence: 0.8
- Reports bugs/console errors by pasting the full raw output — HTTP request/status lines (e.g., `POST http://localhost:3000/... 500`), error type, message, and stack frames with file:line (e.g., `at createJob (jobs.js:18:13)`) — so the assistant can pinpoint the failing line directly. Confidence: 0.95
- Prefers extracting repeated UI blocks (cards, tables, lists) into reusable, prop-driven components (generic columns/rows with per-cell render support, configurable labels) so they can be reused in different contexts with different data; explicitly asks for new UI pieces (e.g., topbar, full page sections) to be built as reusable components and composed together. Confidence: 0.9
- Wants a detailed plan presented and approved before implementation on multi-step feature changes — explicitly asks to be told the plan first "in details" (e.g., layout restructure + auth wiring) and will reject/request changes if the plan isn't what they expected. When asked what they'd change about a proposed plan, they may simply ask for it to be re-presented in full ("give me the plan again") — restate the complete plan, ideally expanded into a structured file-by-file breakdown ending with a verify section, rather than summarizing or asking clarifying questions; wait for the explicit go-ahead before building. Same pattern applies to debugging: asks for the problem to be diagnosed and explained first ("find out the problem and tell me") instead of having fixes applied immediately, expecting the assistant to end by offering to apply the fix. Once approved ("ok fix"), expects the fix applied followed by a concise summary of exactly what was changed ("tell me what you fix"). Critically: do NOT use plan-mode / approval popups for this — the user explicitly rejects them ("dont popup the approval") and wants the plan delivered as plain text in chat, ending with "tell me if you agree and I'll implement" or similar, so they can respond inline. Confidence: 0.9
- For authenticated dashboard chrome (topbar avatar, sidebar profile), prefers wiring real user data from the session (name, avatar image, role) with a working logout dropdown, rather than hardcoded mock users — even when the surrounding UI was previously a static mockup. Confidence: 0.8
- Prefers per-section layouts via route groups so the dashboard renders its own chrome (sidebar + topbar) without inheriting the marketing navbar/footer from the root layout. Confidence: 0.7
- Sometimes explicitly delegates design/content decisions to the assistant ("think yourself") and expects it to make sensible judgment calls on its own — e.g., choosing which extra links/items to add to a menu — without asking for clarification. The exception is a high-level visual/structural fork on a redesign request: when the user asks to "redesign" a page without giving a reference, a single quick design-direction question (2–3 plausible layout options with one-liner descriptions) is welcome — the user will pick one and let the assistant run with the implementation details. Distinguish this from low-level implementation clarifications (e.g., "should this button be primary or secondary"), which the assistant should decide on its own. Confidence: 0.6
- Wants the assistant to verify installed library versions and available exports before writing code against them — explicitly says to "check my package for lib versions" — checking package.json and node_modules type definitions (e.g., confirming a component/icon actually exists) rather than assuming an API is available. Confidence: 0.8
- Prefers compact, tight UI layouts — dislikes large/bulky forms and wants them compacted (smaller padding, smaller/muted labels, tighter grid spacing, shorter textareas, narrower max-width container). Confidence: 0.7
- For every clickable UI element that should navigate, the link MUST actually navigate — flags non-working navigation tersely (e.g., "add company not working - no likable") and expects the assistant to root-cause it by checking the installed library's API (e.g., confirming via `node_modules/.../button.d.ts` that HeroUI v3 `Button` has no `as` prop and always renders a `<button>`), then build a proper `<Link>`-based replacement component (e.g., a `ButtonLink` helper that renders a Next `Link` with the same visual class names as HeroUI variants like `button button--primary`) and use it in place of any `Button as={Link}` pattern. The same fix should be applied across every affected call site, not just the one reported. All in-content navigation (including empty-state CTAs inside forms, error-state "Back" links, etc.) must use Next `<Link>` — never raw `<a href>` tags, even for static-looking internal routes, to keep the SPA navigation behavior consistent. Confidence: 0.85
- Prefers dedicated pages over modal popups for create/edit flows — when iterating on a flow that already uses a modal, explicitly asks to convert it ("no popup model instead edit the page"): the action button should navigate (`router.push`) to a dedicated route (e.g., `/dashboard/[entity]/new`, `/dashboard/[entity]/[id]/edit`) and that page should own the form, validation, submit, and post-save redirect — leaving confirmation dialogs (delete) as the only modals on the page. Confidence: 0.85
- Avoids unnecessary component extraction for single-use UI — if a piece (e.g., a form) is only used by one page, prefers inlining it into that page and deleting the separate component file rather than adding indirection. Confidence: 0.8
- When a diagnosis contradicts their experience, pushes back tersely (e.g., "there is no update job") and expects the assistant to re-verify the claim against the actual codebase — including the other side of the stack (frontend action exports, backend route handlers, data shapes like `_id` vs `id`) — and answer with concrete evidence (file paths, line numbers, signatures) instead of restating the original conclusion. When a client-side action is failing silently, the root cause is often on the server — grep the Express `index.js` for the actual route handlers (`app.get`, `app.post`, `app.put`, `app.delete`) and confirm every HTTP verb the client uses has a matching handler, then add the missing routes mirroring the existing patterns (strip `_id`/`id` from body, use `ObjectId(id)` for the Mongo filter, return 404 on no match). Same audit applies across entity types (jobs, companies, etc.). Confidence: 0.7
- Wants the "return to where you came from after sign-in" flow to be universal — applies not just to proxy/middleware redirects on protected dashboard routes, but to ANY auth-gated action on ANY page (e.g., public job page Apply/Save buttons, "Sign in to [action]" CTAs everywhere). Client components that gate actions by auth should themselves construct `/auth/signin?next=<encodeURIComponent(window.location.pathname)>` on click and use `router.push` (not `window.location.href` which forces a full page reload) — they should not rely on the proxy to add the `?next=` param. Confidence: 0.8
- While debugging, explicitly asks for console.log instrumentation to be added alongside the actual fix (e.g., "put console logs and fix id problem") — logs at key points like submit start, outgoing payload, server responses, and caught errors, so the flow can be traced. - Acts on issues the assistant proactively flags: after being told about a latent bug (e.g., MongoDB documents using `_id` vs mock data using `id`), immediately asks for it to be fixed too instead of leaving it as a future note — expects flagged risks to become real, robust fixes (e.g., a shared helper that handles both data shapes) applied across all affected call sites. The same `_id`/`id` mismatch is consistently treated as a system-wide issue: introduce a single shared getter (`getJobId`, `getCompanyId`) in a common lib file (e.g., `lib/jobstruture.js`, `lib/companies.js`), and use it everywhere a job/company is referenced (page loaders, table action handlers, edit redirects, delete handlers, status-toggle handlers, form submissions) — never reference `job.id` or `company.id` raw, never duplicate the helper inline in components/pages.
