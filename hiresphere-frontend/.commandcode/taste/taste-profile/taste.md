# Taste Profile
- When requesting UI work, prefers UI-only implementations with no business logic or data fetching wired in (static mockups / visual design only), but still expects UI-level interactivity such as modal open/close state to work (e.g., via controlled overlay state). Confidence: 0.8
- Prefers building UI with HeroUI v3 (`@heroui/react`) components and Gravity icons (`@gravity-ui/icons`). Confidence: 0.9
- Expects navigation/sidebar links to be fully functional even in UI work: real route paths, working navigation via framework router (e.g., Next.js `Link`), active-state highlighting based on the current path, and missing routes resolved (e.g., by creating placeholder pages) so every link works. Confidence: 0.8
- Likes to attach a reference image/screenshot of the desired design and asks the assistant to recreate it pixel-for-pixel. Confidence: 0.8
- Reports bugs/console errors by pasting the full raw output — HTTP request/status lines (e.g., `POST http://localhost:3000/... 500`), error type, message, and stack frames with file:line (e.g., `at createJob (jobs.js:18:13)`) — so the assistant can pinpoint the failing line directly. Confidence: 0.95
- Prefers extracting repeated UI blocks (cards, tables, lists) into reusable, prop-driven components (generic columns/rows with per-cell render support, configurable labels) so they can be reused in different contexts with different data; explicitly asks for new UI pieces (e.g., topbar, full page sections) to be built as reusable components and composed together. Confidence: 0.9
- Wants a detailed plan presented and approved before implementation on multi-step feature changes — explicitly asks to be told the plan first "in details" (e.g., layout restructure + auth wiring) and will reject/request changes if the plan isn't what they expected. When asked what they'd change about a proposed plan, they may simply ask for it to be re-presented in full ("give me the plan again") — restate the complete plan, ideally expanded into a structured file-by-file breakdown ending with a verify section, rather than summarizing or asking clarifying questions; wait for the explicit go-ahead before building. Same pattern applies to debugging: asks for the problem to be diagnosed and explained first ("find out the problem and tell me") instead of having fixes applied immediately, expecting the assistant to end by offering to apply the fix. Once approved ("ok fix"), expects the fix applied followed by a concise summary of exactly what was changed ("tell me what you fix"). Confidence: 0.9
- For authenticated dashboard chrome (topbar avatar, sidebar profile), prefers wiring real user data from the session (name, avatar image, role) with a working logout dropdown, rather than hardcoded mock users — even when the surrounding UI was previously a static mockup. Confidence: 0.8
- Prefers per-section layouts via route groups so the dashboard renders its own chrome (sidebar + topbar) without inheriting the marketing navbar/footer from the root layout. Confidence: 0.7
- Sometimes explicitly delegates design/content decisions to the assistant ("think yourself") and expects it to make sensible judgment calls on its own — e.g., choosing which extra links/items to add to a menu — without asking for clarification. The exception is a high-level visual/structural fork on a redesign request: when the user asks to "redesign" a page without giving a reference, a single quick design-direction question (2–3 plausible layout options with one-liner descriptions) is welcome — the user will pick one and let the assistant run with the implementation details. Distinguish this from low-level implementation clarifications (e.g., "should this button be primary or secondary"), which the assistant should decide on its own. Confidence: 0.6
- Wants the assistant to verify installed library versions and available exports before writing code against them — explicitly says to "check my package for lib versions" — checking package.json and node_modules type definitions (e.g., confirming a component/icon actually exists) rather than assuming an API is available. Confidence: 0.8
- Prefers compact, tight UI layouts — dislikes large/bulky forms and wants them compacted (smaller padding, smaller/muted labels, tighter grid spacing, shorter textareas, narrower max-width container). Confidence: 0.7
- For every clickable UI element that should navigate, the link MUST actually navigate — flags non-working navigation tersely (e.g., "add company not working - no likable") and expects the assistant to root-cause it by checking the installed library's API (e.g., confirming via `node_modules/.../button.d.ts` that HeroUI v3 `Button` has no `as` prop and always renders a `<button>`), then build a proper `<Link>`-based replacement component (e.g., a `ButtonLink` helper that renders a Next `Link` with the same visual class names as HeroUI variants like `button button--primary`) and use it in place of any `Button as={Link}` pattern. The same fix should be applied across every affected call site, not just the one reported. All in-content navigation (including empty-state CTAs inside forms, error-state "Back" links, etc.) must use Next `<Link>` — never raw `<a href>` tags, even for static-looking internal routes, to keep the SPA navigation behavior consistent. Confidence: 0.85
- Prefers dedicated pages over modal popups for create/edit flows — when iterating on a flow that already uses a modal, explicitly asks to convert it ("no popup model instead edit the page"): the action button should navigate (`router.push`) to a dedicated route (e.g., `/dashboard/[entity]/new`, `/dashboard/[entity]/[id]/edit`) and that page should own the form, validation, submit, and post-save redirect — leaving confirmation dialogs (delete) as the only modals on the page. The "no popup" preference extends to delete/destructive actions too: when the user lumps update + delete together ("company update still on popup ? no popup and delete btn not working"), they also want the delete-confirm to be an inline panel on the same page (not a HeroUI `Modal`), not just create/edit flows. Confidence: 0.85
- Avoids unnecessary component extraction for single-use UI — if a piece (e.g., a form) is only used by one page, prefers inlining it into that page and deleting the separate component file rather than adding indirection. Confidence: 0.8
- When a diagnosis contradicts their experience, pushes back tersely (e.g., "there is no update job") and expects the assistant to re-verify the claim against the actual codebase — including the other side of the stack (frontend action exports, backend route handlers, data shapes like `_id` vs `id`) — and answer with concrete evidence (file paths, line numbers, signatures) instead of restating the original conclusion. When a client-side action is failing silently, the root cause is often on the server — grep the Express `index.js` for the actual route handlers (`app.get`, `app.post`, `app.put`, `app.delete`) and confirm every HTTP verb the client uses has a matching handler, then add the missing routes mirroring the existing patterns (strip `_id`/`id` from body, use `ObjectId(id)` for the Mongo filter, return 404 on no match). Same audit applies across entity types (jobs, companies, etc.). Confidence: 0.7
- While debugging, explicitly asks for console.log instrumentation to be added alongside the actual fix (e.g., "put console logs and fix id problem") — logs at key points like submit start, outgoing payload, server responses, and caught errors, so the flow can be traced. Console logs are wanted during debugging even if cleaned up later. Also asks for payload logging during ordinary feature development, not just debugging — e.g., "when submit add company and console log the payload": log the full form-data object (with a labeled prefix like `[RegisterCompanyModal] Payload:`) on submit so they can verify its shape before any backend wiring exists. Confidence: 0.8
- Acts on issues the assistant proactively flags: after being told about a latent bug (e.g., MongoDB documents using `_id` vs mock data using `id`), immediately asks for it to be fixed too instead of leaving it as a future note — expects flagged risks to become real, robust fixes (e.g., a shared helper that handles both data shapes) applied across all affected call sites. The same `_id`/`id` mismatch is consistently treated as a system-wide issue: introduce a single shared getter (`getJobId`, `getCompanyId`) in a common lib file (e.g., `lib/jobstruture.js`, `lib/companies.js`), and use it everywhere a job/company is referenced (page loaders, table action handlers, edit redirects, delete handlers, status-toggle handlers, form submissions) — never reference `job.id` or `company.id` raw, never duplicate the helper inline in components/pages. Normalize on load (map `_id` → `id`) so all downstream handlers can rely on `.id` being present, but still call the helper for safety. The "canonical id" for an entity is the user-facing/business-level identifier (e.g., a slug-style `companyId` like `cmp-crane-and-weaver-co-801`), NOT the Mongo `_id` — that slug is what appears in URLs, route params, foreign keys on related entities (jobs.companyId), lookups, and POST/PUT/DELETE bodies, and the server's update/delete routes must accept it (query by the slug field, with a fallback to `_id` for backward compat when the param is a valid ObjectId). Confidence: 0.8
- Skeptical of architectural abstractions by default — questions whether React Context is even needed ("i dont think here react context need here at all") when simpler mechanisms suffice; prefers lean state flow (props, direct fetching, server components/actions) over global providers for narrow-scope state, and wants the abstraction fully deleted once its job is replaced rather than kept as dead scaffolding. Confidence: 0.7
- Proactively requests dead-code/over-computation audits ("find useless or over compute code and give me a list") — values flagging never-called functions and the helpers only they consume, pointless useMemo/useCallback ceremony on small lists, redundant/unreachable validation branches (e.g., disabled submit + warning banner + toast check), leftover console.log/debug statements, stale mock-data remnants after migrating to real APIs/server actions, and payload-shape hacks — presented as a reviewable list before any refactor is applied. Confidence: 0.8
- Scopes requests incrementally: when a bigger feature depends on something not built yet (e.g., recruiter can only post for their company, real company profile "later"), explicitly asks for just the minimal piece now ("now only add company id as in form data") — stamp the field into the payload/form state via the current mock constants and defer full wiring until the real source exists. However, once a real source becomes available (e.g., `fetchCompanies` exists and the user can register companies), the mock placeholders should be removed entirely and replaced with a real `companies` prop plumbed from the page server-component through the form — no half-mock, half-real state. Same for any helper that depended on the mock (e.g., `MOCK_COMPANY.plan` in `getPlanUsage`) — refactor to take the real value as a parameter with a sensible default. Confidence: 0.7
- When current work stands in for unbuilt infrastructure (e.g., MOCK_COMPANY.id as placeholder companyId until company profiles exist), asks the assistant to spell out the future migration plan ("in future ... so whats the plan for that") — expects a phased roadmap grounded in what actually exists in the codebase today: a short current-state summary, ordered phases (create → read path → replace mocks), and explicit open architectural decisions flagged for them to decide (e.g., keep Express+Next server actions split vs consolidate into Next route handlers). Confidence: 0.6
- Declined switching into formal plan mode when asking for the roadmap — prefers plans delivered as an inline chat response (after quick grounding reads of the relevant files) ending with an offer to start, rather than entering a dedicated planning mode. Confidence: 0.5
- Frames new feature requests by analogy to existing in-app patterns and expects them mirrored exactly — e.g., "Add Company" button + register modal "like the job flow" and per-company profile views "like today's page"; when a reference screenshot matches an existing component, reuse that component (e.g., `RegisterCompanyModal`) instead of building a new one. Confidence: 0.7
- Organizes entity management as a list page plus a dynamic detail route: pre-creates the `[id]/page.jsx` placeholder route themselves, expects each card/list item to link to `/dashboard/mycompany/[id]`, the detail view reusing the shared profile component for a hit and rendering a "Company not found" card with a back link for a miss (same pattern as the edit-job page). Confidence: 0.6
- Wants forms submitted via a real `<form onSubmit>` with `e.preventDefault()` and `type="submit"` buttons — not just button onPress handlers. Every create/edit/detail page should have a consistent "Back to [List]" link in the top-left corner before the form, using the shared `ButtonLink` helper with `variant="ghost"`, `size="sm"`, an `ArrowLeft` icon, and `text-muted-foreground hover:text-white` styling — the same pattern across new pages, edit pages, and detail pages, never hand-rolled per page. Confidence: 0.75
- Expects client-side required-field validation on form modals: validate all fields before submit, block submission with per-field error messages below the inputs, red borders on invalid fields, and clear individual errors as the user types. Confidence: 0.7
- When a UI piece is missing from a modal/form they're iterating on, requests it tersely as an incremental add-on ("modal need tagline") rather than a full spec — expects the field slotted into the form state, layout, and payload in one pass. The same terse add-on pattern applies to whole pages ("add job page no back to page link - add thos" with typos): one short sentence, possibly with typos, naming what's missing and expecting the assistant to pick a reasonable implementation matching the existing patterns in the codebase without re-asking. Requests often bundle two related fixes into one message ("add job also need company selection or mandatory filed check" — pick the most aligned interpretation, do both). Confidence: 0.7
- Prefers URL routes to match the verb on the action button that triggers them — e.g., an "Update" button should navigate to `/[entity]/[id]/update` not `/edit`. When the route name and the button label diverge, rename the route folder to match (and update internal copy/labels for consistency) so the URL the user types mentally (or hand-types) lines up with the visible affordance. Confidence: 0.6
- For unexpected visual/UI outcomes, reports tersely with minimal detail and no diagnostics ("size cover but width not boraden", later "cover but in view modal dont get big?" when the first fix didn't take effect), expecting the assistant to autonomously root-cause it — including digging into the installed library's CSS/source in node_modules to see what the prop/class actually generates — and apply the corrected fix in one pass rather than asking clarifying questions. (Contrast with runtime/console errors, where they paste full raw output.) Confidence: 0.6
- Expects visual/UI fixes to be proven in a real browser, not just asserted: for layout/rendering bugs, drive a headless browser (agent-browser CLI; install locally under `~/.commandcode/tools` when global npm install fails on permissions) against the running dev server — open the exact route, snapshot/click through the UI, screenshot before/after, and `eval` JS to walk classes/computed styles up the ancestor chain until the true constraint is identified — then confirm the fix both visually (dimensions, internal scrolling) and functionally (empty submit shows per-field errors, filled submit logs the expected payload) before reporting done. Confidence: 0.6
- When asked for a commit message, prefers conventional-commit style: a short imperative `type: ...` subject (e.g., `feat: rebuild company and job flows with API-first data`), a blank line, a short prose summary, then structured bullet sections (e.g., `Highlights:`, `Server:`, `Cleanup:`) grouping the changes. Does NOT want any `Co-authored-by:` trailer — explicitly told to "nover give co-auth" and wants the assistant to drop it going forward. Confidence: 0.9
- Asks for commit messages in a very terse, lowercase, no-punctuation style (e.g., "give me commit msg", "add job page no back to page link - add thos") but still expects a fully-formed, well-structured output — the brevity of the prompt is not a signal that the response should be brief too. Confidence: 0.7
- When making rename/refactor requests (e.g., "NEXT_BETTER_AUTH_URL and NEXT_BETTER_AUTH_CLIENT_URI - changes"), the request is so terse that the destination name is genuinely ambiguous — the user is comfortable being asked a multiple-choice clarifying question via the question tool with 2-3 plausible options (each with a preview of the resulting env file) and will pick one without re-explaining. The assistant should still do a quick grep of the codebase first to see what the code currently references (so the offered options align with what would actually work), then ask. Confidence: 0.7
- Before applying a rename/refactor that crosses file boundaries (env var names, exported symbols, route paths), expects the assistant to audit every call site first — grep the whole frontend (and the server if relevant) for the old name, confirm the new name aligns with what the code already reads, and only then make the edit in one pass. Renames should never be applied blindly or partially. Confidence: 0.7
- Treats browser-exposed env vars (anything with `NEXT_PUBLIC_` prefix) as a security/deploy concern on Vercel and prefers dropping the public prefix on env vars that only need to be read server-side (e.g., API base URLs consumed by `"use server"` action files) — renames them to plain unprefixed names (e.g., `BETTER_AUTH_CLIENT_URI` instead of `NEXT_PUBLIC_BETTER_AUTH_CLIENT_URI`). The exception is code that genuinely runs in the browser and needs the value at build time (e.g., the Better Auth client config in `lib/auth-client.js`): there the `NEXT_PUBLIC_` prefix is kept because Next.js will inline `undefined` otherwise — the user accepts this trade-off when the assistant explains the build-time constraint. When asked to drop the public prefix, expect the assistant to split the rename: prefix-stripped vars for server-only consumers, prefix-kept vars for browser consumers, with both naming sets in the same `.env` file. Confidence: 0.8
- Prefers domain-specific env var names over vendor-specific ones — when a value (e.g., an API base URL) is used by code outside a single library's boundary, names it by purpose (`NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_API_URL`) rather than by the consuming library (`NEXT_PUBLIC_BETTER_AUTH_URL`, `BETTER_AUTH_CLIENT_URI`). When presented with three options for resolving a naming conflict, picks the option that drops the library prefix and uses purpose-based names — accepting the trade-off of keeping the `NEXT_PUBLIC_` prefix on URL values that aren't actually secrets, because the naming clarity outweighs the theoretical exposure. Confidence: 0.7
